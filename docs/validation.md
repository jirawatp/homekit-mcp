The gateway, HTTPS client and process entrypoints gained dependency seams (`GatewayDependencies`, an injectable request factory and bounded-file access, `Runtime`) so security and error handling run against in-memory fakes. Entry detection uses Node's built-in `import.meta.main`, which also works for extensionless and symlinked launches; subprocess tests cover those launches but only reach argument refusal. Fake TLS primitives exercise the certificate checks, and the real parsers are only given garbage input. The default file opener is proved with harmless temp files and bounded `node` child processes: a symlink to an otherwise valid file is refused (`O_NOFOLLOW`, `ELOOP`) and a FIFO is opened without blocking and then refused (`O_NONBLOCK`); removing either flag from the compiled output was verified to fail the tests quickly. Synthetic token-format temp files exist during tests and are deleted afterwards; **no real credential, key, certificate or listener is created**, so real TLS behavior is **not** established.

Hardening made along the way: non-finite certificate dates are rejected; helper/server close errors cannot become unhandled rejections; the HTTPS client also rejects a response that closes before `end` (defense in depth, since Node's HTTP parser already errors on truncated bodies); and any failed start closes every already-created helper, TLS client, server and handle exactly once. Startup refusal emits fixed diagnostics only, with no paths or error text: normally one line, and two lines if cleanup also fails (a fixed shutdown-error line followed by the fixed refusal line).

Native scope: `native/Sources/BridgeCore/*.swift` (`BridgeCore.swift`, `SessionCoordinator.swift`, `StdioServer.swift`), measured by `swift test --enable-code-coverage` and `scripts/native-coverage-check.mjs`. LLVM reports lines, functions and regions for Swift; it reports no branches. The input-framing figures include the Foundation-only `BridgeFixture` run as a subprocess by the tests. **Not covered:** `native/Sources/Helper` (the Mac Catalyst app, `App.swift` and `HomeKitController.swift`), which the package does not compile, and every real HomeKit, camera or device interaction. Catalyst app coverage is not established; its build is compile-only and it was never launched. Current per-file and global native figures are in the table above (2026-10-22 consolidated run); the 90% gate applies to the global total, not per file. Swift branch coverage is unsupported by the tool.

Native check scripts: `scripts/test-native.sh` and `scripts/coverage-native.sh` both source `scripts/native-env.sh`, so every SwiftPM call (the test run and the later `--show-codecov-path` lookup) uses the same project-local scratch, cache, config, security and clang/SwiftPM module-cache paths under `native/.build`. `coverage-native.sh` stops with exit 2 if the reported coverage JSON does not exist, and also refuses a report older than the current run (a freshness marker is created in the project's own build directory first; nothing is deleted). The gate CLI detects that it is the entry script by comparing real paths instead of `import.meta.main`, which is `undefined` on older Node and would have let the gate exit 0 having checked nothing; only Node 22.19.0 was tested, and the `>=22.19.0` engine floor is advisory (npm does not enforce it by default). `npm run test:gates` (19 tests) covers the gate's evaluation and CLI, including a real-inventory check that requires each BridgeCore source individually, relative-path and symlinked launches, and `coverage-native.sh` driven by a stub `swift` in an isolated temporary project (scoped environment even when the caller exports others, below-90 and missing-source reports, stale, missing, empty and multi-line report paths, a failing test run, argument forwarding). The 90% floors, the exact-inventory check and the absence of exclusions are unchanged. The freshness check was verified by that stub regression and then by one real `npm run coverage:native` run on 2026-10-22 (82 of 82 tests, exit 0, report newer than the marker, marker cleaned up), with the 19 gate tests passing at the same time and all 19 input-file hashes unchanged before and after. That real run exercised the passing path only; the stale-report refusal itself is covered by the stub regression, not by the real command.

### Native hardening (2026-10-22): what is and is not tested

Tested Foundation logic, in `native/Sources/BridgeCore` (measured by the unchanged 90% lines/functions/regions gate; figures in the table above):

- `StdioServer.swift`: exactly-once request settlement (`OneShot`); duplicate synchronous and asynchronous callbacks and late callbacks after a timeout are discarded; a callback racing the deadline resolves to one outcome; only the loop writes; encoding failure, output-write failure and input failure close the transport once, with no later dispatch and no further write attempt; injected input/output/encoder/timeout make these cases deterministic. A subprocess test through the real `BridgeFixture` proves the default writer fails closed when the response pipe breaks while stdin stays open.
- Response ceiling and write loop (`StdioServer.swift`): a frame of exactly 1,048,576 bytes (newline included, the TypeScript client's limit) is written whole and one byte more is replaced by a small `response_too_large` error that keeps the request id and leaks no content; a smaller injected ceiling covers the exact boundary, and the transport fails closed if the replacement does not fit, cannot be encoded or cannot be written. `writeAll` is tested with an injected write function for short writes (every byte delivered in order from the correct offset), `EINTR` retry, zero-progress (fails on the first zero, no spin) and error returns. **Limits:** the ceiling is checked after encoding, so it does not bound encode-time memory (only indirectly bounded by the 256-accessory allowlist and scalar filters), and the native layer still does not cap service/characteristic counts or text lengths; a real pipe-exhaustion or real zero-progress condition was not reproduced.
- `SessionCoordinator.swift` (`SessionCoordinator`, `RefreshTracker`): deny-all start, enable/disable, failed and successful configuration reload, authorization revocation, home-data update, session change during a read, duplicate/unknown/late characteristic callbacks, refresh deadline and the 256-characteristic bound, and cache admission only for a current, enabled, authorized, allowlisted session.

**Not tested, and not covered by any Core percentage:** `native/Sources/Helper/HomeKitController.swift` and `App.swift` (the Catalyst app) are uninstrumented and were only compiled/typechecked. The glue between Apple's objects and the coordinator is unverified at runtime: `HMHomeManager` construction and delegate callback ordering, `HMHomeManagerAuthorizationStatus` mapping, `HMCharacteristic.readValue` behavior, the UI thread/main-queue hops, the file picker and sandbox access, and the foreground consent flow. The real-world effect of revocation, reload and late device callbacks is therefore still unproven until the signed-app device validation below. The helper's behavior was intentionally preserved; one deliberate change is that `StdioServer.start` now ignores `SIGPIPE`, so a vanished reader surfaces as a write failure and an orderly close (session disabled, app exits) instead of abrupt termination.
